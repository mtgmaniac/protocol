## 1. Resume guard (built)

Rules: TRUTH "Resume guard"; ruling and the points where the build differs from
the proposal: DECISIONS_RESOLVED G-48. Gate `resume guard` (real menu buttons,
separate processes, four deliberate breaks).

- CONTINUE writes `user://resume_guard.json` before its screen loads. If it is
  still set at the next launch, RESUME EARLIER POINT appears under CONTINUE with
  "The last resume didn't get past loading." It puts the previous screen's save
  back and the menu says "Restored the rewards after battle 8." CONTINUE then
  resumes it. Screens: `debug_artifacts/resume_guard/` (local, git-ignored).
- **The "restore doesn't work" playtest report.** Found and fixed a real bug in
  the same code: through the real menu, CONTINUE never restored a mid-battle
  round. `SceneManager.go_to_battle` saved a fresh battle entry before the
  battle scene could take the checkpoint, so the battle restarted at round 1 on
  the checkpoint's mid-battle run state. Same cause as the guard's problem
  statement (a save written before the destination loads). The older gates
  never pressed the menu button. If the report meant something else (the page
  itself not coming back after an app switch), that is item 3 and the guard
  does not cover it.

**Waiting on Kev (each is recorded in G-48 as his to overturn):**
1. `run.json.bak` could not be the earlier point (it is the previous write, and
   screens save twice on entry), so the guard keeps its own `run.json.prev`.
   Alternative: change what `.bak` keeps, which amends G-21's write-safety rule.
2. The marker also clears when the resumed screen loads cleanly, not only on
   run save progress. Without that, reloading twice on one screen offered a
   rewind (replay a won battle, re-throw seen dice). Cost: a stall that starts
   after a clean load gets no option.
3. RESUME EARLIER POINT is two taps (restore, read the notice, CONTINUE).
4. It goes back one screen, and a restored battle starts from its entry.
5. No option when there is nothing earlier (a hang on the run's first battle).

## 3. App-switch freeze (report only)

`docs/audits/APP_SWITCH_FREEZE_2026-10-06.md`. The audit's cause stands with
two corrections: it is not visibility or focus handling (a 60 s hidden page
resumes cleanly), and the game does not stop: after a WebGL context loss the
loop, input and audio keep running under a dead picture, and the engine never
rebuilds even when the browser returns the context. Confirmed by reading the
shipped export and forcing the loss in a desktop browser. Not confirmed on the
phone; the report has a 30-second check. Proposed fix: a reload overlay in
`web/shell.html`, optionally reloading and resuming by itself.
